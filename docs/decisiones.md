# Decisiones técnicas

> Es un **historial**: cada fila explica por qué se decidió algo en su momento. Si dos filas se contradicen (p. ej. fondos globales frente a fondos por mes), vale la **más reciente**; el estado actual está en [arquitectura.md](arquitectura.md) y [reglas-fondos.md](reglas-fondos.md).

| Decisión | Motivo |
|---|---|
| npm como gestor | Ya instalado, sin lockfile previo. |
| Supabase CLI como devDependency (`npx supabase`) | Sin instalación global; versión fijada en el lockfile. |
| `@hookform/resolvers@5` | La v6 genera conflicto de peer dependencies opcionales con `effect`; la v5 es compatible con Zod 4. |
| Zod 4.6.7 | Versiones previas tienen una advisory de alta severidad (consumo de memoria). |
| Paleta B "Índigo" | Elegida por el usuario tras revisar 5 propuestas. Tokens en `src/index.css`. |
| Registro público desactivado | App de uso personal. Usuarios por seed o Studio. |
| Contraseña mínima de 8 caracteres | Endurece el valor por defecto de Supabase local. |
| Modelo con `household_id` | Permite colaboración familiar futura sin rediseñar. Hoy un hogar por usuario. |
| Motor de asignación de fondos en SQL | Una sola fuente de verdad; el TypeScript solo previsualiza. |
| Guardia de entorno (`src/lib/env.ts`) | Desarrollo solo contra Supabase local; producción nunca contra localhost. |
| Fondos: sin gasto "sin imputar" | Corrige la ETAPA 2. El General absorbe el excedente y puede quedar negativo; si ningún fondo admite la combinación, se bloquea. Ver [reglas-fondos.md](reglas-fondos.md). |
| `[auth.email] enable_signup = true` | Ese ajuste habilita el proveedor de correo; en `false` bloquea también el inicio de sesión (`email_provider_disabled`). El registro público lo bloquea `[auth] enable_signup = false`. |
| Credenciales E2E en `.env.local` | Las pruebas Playwright leen `E2E_USER_EMAIL`/`E2E_USER_PASSWORD` de un archivo no versionado. |
| Respuesta neutra al recuperar contraseña | No revela si un correo está registrado. |
| Sesión "vencida" distinta de "cerrada" | Un `SIGNED_OUT` sin cierre explícito del usuario lleva a `/sesion-expirada`. |
| Proyección de cierre y ritmo ideal | Se muestran como estimaciones. |
| Sin conversión USD | El prompt original no permite inventar tipos de cambio. |
| Flujo de medios de pago (Sankey) | Se mostró en la propuesta visual a pedido del usuario, pero el último prompt vuelve a excluir gráficos por medios de pago: **no se implementó**. |
| Comparación con el mes calendario anterior | Si el rango es un mes completo se compara con el mes previo; si no, con un rango de igual duración. |
| Reordenar prioridad con simulación | `reorder_funds` admite dry-run: se explica el efecto antes de aplicar. |
| Foco al cerrar diálogos | `Modal` devuelve el foco al control que lo abrió. |
| Agregaciones del Dashboard en SQL | `dashboard_panel` (antes `dashboard_resumen`): ningún KPI depende del límite de 1000 filas del API. |
| `leerTodo` falla en lugar de truncar | Toda lectura que alimenta una cifra verifica el total declarado por el servidor. |
| Limpieza compensatoria de comprobantes | Intención previa + borrado tras fallo + tareas reintentables; nunca se borra un archivo en uso. |
| Usuario E2E propio y reinicio por prueba | `dev_reset_user` (solo local, en `supabase/fixtures/e2e.sql`) aísla las pruebas del seed demo. |
| Auditoría axe sin excepciones | Ver [accesibilidad.md](accesibilidad.md). El tono verde `--ok` se oscureció para cumplir contraste. |
| `verify:security` | Comprueba secretos, migraciones sin datos demo y un build de producción sin URLs locales. |
| Dashboard con filtros cruzados en la URL | Una sola fuente de verdad (`useFiltrosDashboard`) y una sola RPC (`dashboard_panel`) alimentan KPIs, gráficos, Top 5, recientes y fondos: no pueden divergir y las respuestas atrasadas no sobrescriben a las recientes (clave de consulta con filtros + cancelación). |
| Presupuesto consolidado con filtros | El presupuesto es siempre el del período completo; el gasto con filtros se muestra aparte («no se puede repartir por los filtros»). Registrar gastos nunca se bloquea por exceso. |
| Tooltip de la dona externo | El detalle del segmento se muestra fuera del anillo (lateral) para no tapar el total central; también se activa por teclado desde la leyenda. |
| Animaciones solo al abrir | `.anim-*` se desactivan en `data-state=closed` para que Radix no retenga la capa (un Escape rápido debe cerrar el diálogo). |
| Exportaciones en el navegador | CSV (`gasto-deejota-gastos-AAAA-MM-DD.csv`) y respaldo JSON (`…-respaldo-…json`, `version_esquema` 1) se arman con la sesión del usuario (RLS) leyendo por tandas con `leerTodo`; excluyen autoría, rutas de comprobantes, tokens y claves; las celdas CSV neutralizan fórmulas. Sin `service_role`. |
| Actividad de solo lectura | Se lee `audit_logs` (propietario) con paginación y filtros; los eventos sin usuario (semillas/cargas) son «sistema» y se ocultan por defecto. No hay escritura ni borrado desde la app. |
| Catálogo: propuesta G «Estudio de color» implementada | Elegida entre A–H. Lista + editor en línea + vista previa en vivo en claro y oscuro (nombres reales, sin importes). Migración aditiva `20261029000001_catalogo_color_hex`: `color_hex` (`#RRGGBB` en mayúsculas, con CHECK) en ámbitos, categorías y medios; `color_mode` (`own`/`inherit`) en categorías. `color_token` se conserva como respaldo. |
| Color efectivo resuelto en un solo lugar | `useCatalogo` entrega `color_css` (propio, heredado del ámbito o equivalente del token) y toda la app lo consume; los tonos por tema (`domain/color.ts`) garantizan 4.5:1 en texto y 3:1 en íconos, calculados sobre valores de 8 bits. En tema oscuro los HEX se aclaran con `--k-mix`/`--k-tint`. |
| Cambiar un color no toca el histórico | Los gastos guardan ids, no colores: recolorear nunca altera importes ni períodos cerrados. Armonizar es reversible desde el aviso. |
| Refinamiento visual Dashboard y Gastos | Barra única de filtros (Período en popover, Día, Ámbito, Categoría, Subcategoría, Medio, Tipo, Limpiar, Registrar) sin chips duplicados; indicadores con acento; Presupuesto consolidado con encabezado degradado y cuadrícula 4×2; tabla de Gastos y detalle por secciones con reparto visual entre fondos. Sin cambios en cálculos ni reglas. |
| Filtros del Dashboard sobre la URL vigente | Las acciones leen `window.location.search` al ejecutarse, no el estado del último render: dos acciones seguidas no se pisan (Limpiar conservaba un período obsoleto). |
| Acentos de color | `.acento-*` (generados con `domain/color.ts`) y `.chip-k` mezclan el color del elemento con el del tema para mantener contraste en claro y oscuro. |
| Aplicación vacía por defecto | `handle_new_user` (migración `20261029000002`) crea solo hogar, membresía y perfil; `seed.sql` crea solo la cuenta de acceso local. `bootstrap_catalog` se conserva únicamente para fixtures. Sin Fondo General inicial: el motor ya contempla su ausencia (GD001 explica qué falta). |
| Fixtures de pruebas aisladas | `supabase/fixtures/e2e.sql` (funciones `dev_*`) se carga en `global-setup` y se retira en `global-teardown` junto con el usuario E2E; los pgTAP crean su propio catálogo de partida. `verify:seed` falla si queda cualquier rastro. |
| Fondos en tabla compacta y «Eliminar fondo» | Tabla (tarjetas en móvil) con General primero y el resto por prioridad (orden de creación por defecto, reordenable por menú o arrastre). `delete_fund` es atómica y con simulación: no elimina el General ni fondos con historial cerrado (ofrece desactivar); un fondo sin uso se elimina; con imputaciones abiertas exige un destino que admita todos esos gastos y recalcula los períodos abiertos con el motor (los gastos y sus importes no cambian). El destino garantiza cobertura; la imputación final la decide el motor según prioridades vigentes. |
| Íconos ampliados y selector único | 119 íconos con identificador estable, nombre en español, 12 secciones y sinónimos (`domain/iconosCatalogo.ts`); migración `20261030000001` amplía `is_valid_icon` conservando las claves antiguas (`home` se muestra como `house`). `SelectorIcono` (contraído/expandido de altura fija, búsqueda sin tildes, secciones, teclado) sirve a Ámbitos, Categorías, Subcategorías, Medios de pago y Fondos. Las sugerencias son locales (`sugerirIconos`): preseleccionan solo elementos nuevos y la elección manual siempre gana. |
| Prototipos descartados retirados | Los prototipos HTML de Catálogo, Fondos, Salud y Dashboard (rechazados o ya implementados) se eliminaron del árbol; siguen en el historial de Git (commit «Conserva los prototipos descartados…»). |
| Importes con contrato único | `src/lib/importe.ts`: coma o punto decimal, miles explícitos, ambiguos y malformados con error visible (nunca se adivina), límite numeric(14,2), cálculo en céntimos enteros. |
| Registro global de gastos | Un único `GastoForm` montado por `RegistroGastoProvider`: el + central (móvil) y el botón flotante (escritorio) lo abren sin cambiar de ruta; se ocultan con un diálogo abierto. |
| Tabla o tarjetas según el ancho real | Fondos usa consultas de contenedor y Gastos mide el contenedor (un solo DOM a la vez); la barra lateral es compacta entre 1024 y 1279 px y la inferior cubre hasta 1023 px. |
| Módulos con carga diferida | Cada página se importa bajo demanda; el paquete inicial pasó de 1,61 MB (467 kB gzip) a 278 kB (87 kB gzip). |
| Barra lateral con dos modos | `BarraLateral` + `useBarraLateral`: expandida/compacta con tooltips, preferencia separada para escritorio y pantallas medianas (no se pisan), animación que respeta movimiento reducido. |
| Colores: paleta de 36 y selector compartido | `SelectorColor`/`ColorCompacto`; `is_valid_color` admite #RRGGBB, así los fondos guardan color libre en `color_token`. Subcategorías: `color_mode` (inherit/own) con color efectivo dinámico. |
| Armonizar con selección | `ArmonizarDialog` previsualiza color actual y propuesto, deja escoger y avisa antes de pasar elementos de heredado a propio. La propuesta depende solo de la posición en la lista. |
| Vista previa por período de cambios en fondos | `preview_fund_change` ejecuta la operación real dentro de un bloque que siempre se revierte y devuelve asignado/consumo por período abierto y fondo. |
| Análisis del Dashboard en una fila | Calendario, perfil y ranking (`dashboard_analisis`): los filtros cruzados se aplican en el cliente para que cada gráfico excluya su propia dimensión. El gráfico de flujo se retiró a petición. |
| Gastos imputados | `DetalleFondo`: el reparto sale de las imputaciones guardadas; el motivo solo se explica cuando hay información real (sin reconstruir reglas históricas). |
| Filtros por nombre con varios IDs | Categoría y subcategoría muestran una opción por nombre (`domain/idsFiltro.ts`); elegirla guarda todos los IDs homónimos separados por coma y filtra todos (RPC `dashboard_panel` con `uuid[]`, migración 20261031000004; Gastos con `in`). No se fusionan registros del catálogo. |
| Selector de período con estado | `FiltroFecha` muestra Período abierto/cerrado/futuro bajo el mes (`domain/periodo.ts`, comparación año×12+mes en la zona del perfil). Es solo calendario: no cambia permisos de edición. |
| Tooltips de gráficos | Familia `TooltipGrafico` con variantes evolución, distribución, comparación e histórico; `Hint` no los envuelve de nuevo. |
| Formulario de gasto en cascada | `SelectorChips`: ámbito → categoría → subcategoría y medio de pago con icono, color y orden del Catálogo; descripción, notas y comprobante visibles; la cobertura por fondos sigue en la columna derecha. |
| Fondos independientes por mes | `funds.period_id`: cada fondo es una instancia de UN mes (nombre, prioridad, reglas e importe propios). `ensure_period` ya no crea fondos ni presupuestos; `recalc_period`, `save_fund`, `reorder_funds`, `delete_fund`, `close_period` y `dashboard_panel` se acotan al período. Claves foráneas `(fund_id, period_id)` impiden imputar un gasto a un fondo de otro mes. Un mes sin fondos deja sus gastos «sin fondo» (no se bloquea el registro). |
| Migración de fondos a instancias por mes | Respaldo previo en el esquema `respaldo_fondos` (no expuesto) y en `respaldos/` (ignorado por git). Cada fondo se asignó al mes de su fecha de creación; si no hubiera período se detiene en vez de inventarlo. En esta base: solo octubre 2026 conserva sus 5 fondos; los 70 presupuestos automáticos de otros meses quedaron archivados (no borrados) y los períodos no se tocaron. Reversión: restaurar desde `respaldo_fondos.*`. |
| Copiar fondos entre meses | RPC `copy_funds`: instancias independientes (nombre, icono, color, prioridad, reglas e importe editable; sin gastos ni consumo), idempotente (`funds.copied_from` + índice único por mes) y sin sobrescribir: omite repetidos, mismo nombre o un segundo General. |
| Planificación mensual | `period_plans` + RPC `save_period_plan` / `planning_summary`; asistente de tres etapas (fondos, gastos desde plantillas, resumen) que guarda cada etapa y no crea nada sin confirmar. La invitación (`debeInvitar`) es solo dentro de la app, no bloquea y «Cerrar» no completa; `profiles.planning_reminders` controla los avisos. La plantilla `default_fund_id` queda informativa: apunta a un fondo de un mes. |
| Tabla de Fondos equilibrada | `TablaFondos` distribuye por ancho real del contenedor: ≥1056 px ocho columnas (Fondo 23 · Cobertura 17 · Prioridad 9 · Asignado 10 · Consumido 10 · Disponible 11 · Uso 10 · Acciones 10), 720–1055 px seis columnas con cobertura y prioridad bajo el nombre, y tarjetas por debajo. La cobertura (`domain/cobertura.ts`) sale de las reglas reales de cada fondo: máx. dos etiquetas y «+N» con el detalle (incluye/excluye); sin presupuesto no se muestra porcentaje. |
| Plantillas de gastos y de fondos | Una plantilla es una configuración, no un movimiento ni un fondo asignado: guardarla no toca saldos ni consumos. Gastos: `GastoForm` es el único formulario (modos `plantilla`, `plantilla-editar` y `desde-plantilla` además de los de gasto); `expense_templates.notes`; registrar desde plantilla usa `create_expense` con `template_id` (varios registros permitidos). Fondos: biblioteca global `fund_templates` (+ reglas) con `save_fund_template` y `apply_fund_templates` (atómica, un fondo por plantilla y mes gracias a `funds.template_id` + índice único, un solo Fondo General activo, prioridad sugerida resuelta contra el mes, plantillas inactivas o sin clasificación omitidas con motivo). `FondoForm` sirve a fondo y plantilla (`modo`). Convertir (gasto/fondo → plantilla) copia solo configuración; eliminar una plantilla desvincula sus fondos sin borrarlos. Las altas y reglas de plantillas de fondo solo entran por la función validada. |
| Gestor de plantillas (gastos y fondos) | Las bibliotecas son gestores: secciones expandibles (`SeccionPlantillas`, casilla con estado indeterminado), búsqueda, filtros, selección múltiple que sobrevive a filtros y a contraer secciones, edición inline y resumen/pie con acción principal. Agrupación a partir del catálogo real (`domain/agrupacion.ts`: categoría —los homónimos de distintos ámbitos forman una sola sección—, ámbito, tipo o medio; en fondos: tipo, grupo propio `fund_templates.group_name` o cobertura principal). El orden manual (`reorder_templates` → `sort_order`) es solo presentación: nunca cambia ámbito, categoría ni prioridad financiera; el orden de secciones, la agrupación y el criterio de orden son preferencias del navegador (`usePreferencia`, local; lo expandido, por sesión). Los ajustes inline (importe, fecha, medio; en fondos importe y prioridad propuesta) valen solo para lo que se crea; cambiar la plantilla original exige «Actualizar plantilla con estos valores» con confirmación. Gastos: una fecha general que se aplica solo a las seleccionadas (más fecha individual y «Restaurar sugeridas»; mes corto → último día, visible), revisión previa con la simulación del motor (`preview_expense`) y registro fila a fila con su propia clave de idempotencia: el resultado se informa por fila y se reintenta solo lo pendiente (no usa `apply_template_batch`, que sigue en «Registrar mensuales»). Fondos: `apply_fund_templates` admite `priority` confirmada por ítem; los conflictos (Fondo General, duplicado, nombre repetido, sin clasificación) se muestran antes de aplicar. Moneda: el sistema es solo PEN, así que los totales se muestran en S/ sin subtotales por moneda. |
| Planificación: etapas Gastos y Resumen, plantillas de fondos compactas | El gestor de gastos (`GestorPlantillasGastos`) y el de fondos (`GestorPlantillasFondos`) se incrustan en las etapas de la planificación (el diálogo de biblioteca usa los mismos componentes). Filas tipo tabla con encabezados (≥58 rem / ≥52 rem; por debajo, tarjetas), estados Pendiente/Seleccionada/Registrada/Omitida/Error (gastos) y Disponible/Seleccionada/Aplicada (fondos: verificación + importe real del mes, sin casilla). Fondos: sin secciones por defecto; con pocas plantillas dentro del asistente solo se muestra lo esencial. El Resumen separa gasto total, consumo imputado a fondos (específicos / General) y gastos sin fondo compatible calculando el consumo desde las imputaciones del mes; no hay RPC nueva. Una etapa Gastos revisada puede quedar «Completada» con plantillas opcionales pendientes. Gastos imputados (`DetalleFondo`): diálogo de altura fija (`Modal layout="fijo"`) con zona superior fija, listado con scroll propio y pie con paginación real (10/25/50) que reemplaza filas; la búsqueda (concepto, notas, clasificación, medio) y el orden se aplican a TODOS los movimientos del fondo antes de paginar, con empate determinista. La paginación es del lado del cliente porque el tipo de imputación (directa/compartida/excedente) depende de las imputaciones de todo el período y de las reglas actuales (`admite`); el volumen por fondo y mes es acotado. |
| Paginación unificada y gestor compacto | `Paginacion` (components/ui) es el único paginador: «1–20 de 83 · 20 por página · ‹ 1 2 3 … 18 ›», una fila de 32 px, números inteligentes (`domain/paginacion.ts`) y, en un contenedor estrecho, «n/m». Lo usan Gastos (servidor: `tamano` en la URL, 10/20/50/100), Gastos imputados (cliente, sobre el conjunto completo filtrado y ordenado) y Actividad. Las plantillas mensuales comparten una sola definición de columnas entre encabezado y filas (`COLUMNAS`), nombre en una línea con tooltip, chips acotados a su columna, encabezado de sección de ~40 px, filtros en una fila (`Combobox compacto` con texto corto en el disparador y el nombre completo en el menú) y «Pendientes» como interruptor. Se eliminó el bloque «Fecha general»: la fecha se edita por fila. El gestor se muestra en un diálogo `2xl` (también en la planificación). |
| Acciones por elemento en móvil | `components/ui/AccionesFila` es el único mecanismo: cada fila declara UNA lista de acciones (`AccionFila`: icono, texto, nombre accesible con el elemento, tono, deshabilitada + motivo) que alimenta el panel de tarjeta y el menú de escritorio (`MenuDeAcciones`, con altura acotada al espacio libre y colisiones). En tarjeta, deslizar a la izquierda (`domain/gesto.ts`: intención 10 px, apertura 56 px, horizontal solo si |dx| > 1,6·|dy|, vertical y diagonal son del scroll nativo con `touch-action: pan-y`) o pulsar «Acciones» (`aria-expanded`/`aria-controls`) abre el MISMO panel bajo la fila, con botones de ≥ 44 px; `GrupoAcciones` deja una sola fila abierta y la cierra si cambia su `clave` (búsqueda, filtros, orden, página, período). El gesto nunca ejecuta nada: las acciones destructivas solo abren su confirmación existente. No se captura el gesto sobre controles (`data-sin-gesto`; `data-gesto-ok` lo permite en el botón principal de una fila) ni con ratón en filas arrastrables. Escape (vía `data-captura-escape`, sin cerrar el diálogo contenedor), toque fuera y deslizar a la derecha cierran; el foco vuelve al botón. Gastos conserva Anular/Restaurar (no hay borrado definitivo en esa interfaz). En Catálogo, con la lista más estrecha de 24 rem el panel sustituye a los cinco iconos para que el nombre use la fila. |
| Migraciones: incrementales hasta el primer despliegue | Decisión: **conservar las 24 migraciones incrementales**; no consolidar en un esquema inicial. Motivo: (1) existe una base local con datos reales actualizada migración a migración y una migración inicial nueva no se puede aplicar sobre ella (Supabase la trataría como no aplicada y chocaría con los objetos existentes); (2) no hay ningún proyecto remoto enlazado, pero reescribir el historial no aporta nada que `verify:install` no cubra ya: aplica todo en orden sobre una base vacía, y pasa (RLS, permisos y las pruebas pgTAP). **Después del primer despliegue** ya no es posible reescribir: cada cambio será una migración nueva. Si, ANTES de desplegar y con una base de producción vacía, se quisiera un único script, se generaría con `pg_dump -s` de una instalación verificada y se sustituiría el directorio completo, sabiendo que la base local deberá recrearse (`db:reset`) y que se pierde el historial legible. Versionado: toda migración nueva usa una versión mayor que la más alta existente (hoy 20261103…), aunque el calendario esté antes. |
| Respaldo de la migración de fondos por mes | `20261101000001` crea el esquema `respaldo_fondos` con copias de los datos previos. En una instalación nueva nace vacío y no estorba; en una base existente es el respaldo de esa migración y no se elimina. Se conserva dentro de la migración (no se separa) porque la migración ya está aplicada: editarla la dejaría distinta de lo aplicado. |
| Caché de consultas por usuario | `ConsultasPorUsuario` crea un `QueryClient` nuevo por identidad (y vacía el anterior) en el mismo render del cambio de sesión. Invalidar no basta: los datos viejos seguirían en memoria y se mostrarían hasta el refetch (p. ej. `useHogar`, con `staleTime` de 5 minutos). Las claves de hogar y perfil incluyen el id de usuario como defensa adicional. |
| Alta de catálogo atómica | `create_catalog_item` (SECURITY INVOKER: respeta la RLS; el hogar sale de la sesión) inserta y reordena «Otros» en una sola transacción; antes eran dos peticiones y un fallo de la segunda dejaba el elemento creado con un mensaje de error. Otras secuencias revisadas y NO cambiadas: `colorear` (varios `update` en paralelo; es solo cosmético, la interfaz vuelve a leer el estado real y ofrece deshacer) y `save_fund_template` + `group_name` (el grupo es una etiqueta de organización; un fallo se informa y no afecta importes). |
| Contratos de RPC | `lib/contratos.ts` valida con zod las respuestas de las RPC financieras (gastos, fondos, copias, plantillas, planificación). Un cambio incompatible falla con `ContratoRpcError` (RPC y campo) en lugar de propagarse. `database.types.ts` sigue siendo generado y no se edita. Sin validar todavía: `dashboard_panel` y `dashboard_analisis` (formas grandes, calculadas en SQL). |
| `usePeriodo` llama a `ensure_period_rpc` | Se conserva: la llamada es idempotente (índice único por hogar y mes) y toda pantalla necesita que el mes exista; separar «crear» de «leer» obligaría a decidir en cada pantalla quién lo crea.
